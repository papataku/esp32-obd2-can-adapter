# TX-isolated passive receiver — design evidence

Dedicated candidate, stacked on PR #63 head `f6b0c79c5e52efc77b599287f2b70c8dfdf295b3`.
Current hardware acceptance: **NOT TESTED / vehicle NO-GO until owner/PM completes the runbook**.
No flash, reset, serial connection or vehicle action by implementation agent.

## A selected: remove the controller-to-transceiver TX path

- Repository wiring: `AGENTS.md:36-43`, `include/passive_policy.h:10-13` fix GPIO13=TXD, GPIO15=RX, temporary install sink=GPIO39.
- [M5Dial official pin map](https://docs.m5stack.com/en/core/Dial#pinmap): PORT.A GPIO13/15. [Dial schematic, sheet 2, M1/P4](https://m5stack-doc.oss-cn-shenzhen.aliyuncs.com/499/Sch_M5Dial.pdf): GPIO39/MTCK reaches otherwise unused header P4 pin10, not the Grove CAN TX line. No probe/extension may be attached there during this trial.
- [U179 official product](https://docs.m5stack.com/en/unit/Unit_Mini_CAN) identifies TJA1051T/3 (not the U085 CA-IS3050G). [U179 schematic, sheet 1, U3](https://m5stack-doc.oss-cn-shenzhen.aliyuncs.com/631/SCH_UNIT_Mini_CAN_V1.0.pdf): Grove CAN_Tx→U3.1 TXD, CAN_Rx←U3.4 RXD, U3.8 S grounded; **silent mode is not GPIO accessible**. R1 is 120Ω across CANH/CANL. There is no programmable standby workaround on the supplied wiring.
- [NXP TJA1051 Rev9](https://www.nxp.com/docs/en/data-sheet/TJA1051.pdf), §7.1/Table4 p5: TXD HIGH yields recessive, RX remains active. §7.2.2 p6: TXD internally pulls up to VIO when MCU is high impedance; §7.2.3: transceiver disengages on VCC/VIO undervoltage. These are the reset/power transition assumptions; a GPIO cannot be an active HIGH output before application boot. GPIO13 is not an ESP32-S3 boot strap or standard boot flash/UART pin ([ESP32-S3 datasheet, pin/reset tables](https://www.espressif.com/sites/default/files/documentation/esp32-s3_datasheet_en.pdf)). Unknown bootloaders are rejected by the app-only flash gate.
- `src/passive_rx.cpp:66-105,178-211`: first setup action preloads GPIO13 HIGH before enabling input+push-pull output, selects software-controlled output enable, and verifies its latch AND actual input pad. The LCD is configured directly from schematic GPIO4..9 (lines 40-64). M5Unified and M5GFX board autodetection are not called or linked: cached/wrong board probes can transiently pulse GPIO13 before any later readback. PORT.A is never probed as I2C. IDF4.4.7 requires a nonnegative tx_io ([driver/twai.c:385-432](https://github.com/espressif/esp-idf/blob/v4.4.7/components/driver/twai.c#L385)); install uses GPIO39 while stopped, never GPIO13. **Before `twai_start`, every GPIO matrix TX route is removed**. No physical GPIO carries the running controller's TX, including erratum error flags, ACKs or data.
- `platformio.ini:259-269`: only `passive_rx.cpp` is an application TU. Legacy `can_monitor.cpp:478` NORMAL transition and all query/ARM/lease/BLE paths are excluded, rather than returning early at runtime. `include/passive_build_guard.h` is force-included and poisons transmit, NORMAL, NO_ACK and automatic recovery. Conflicting TX flags fail compilation; `include/passive_policy.h` has immutable static assertions. The linked ELF must contain RX/install/start/stop/uninstall but no TX, recovery, legacy CanMonitor, Signal V2 ARM or BLE symbols (`tools/check_passive_elf.py`). Existing default/active profiles are unchanged.

This is hardware **routing isolation**, not galvanic isolation or a cut TXD wire. Firmware never writes GPIO13 LOW. It removes the specific listen-only erratum's physical path without changing prebuilt HAL or depending on REC. It cannot guarantee safety against arbitrary memory corruption, GPIO electrical faults, wrong wiring/module or altered ROM/bootloader behavior.

## Continuous checks and failure handling

`src/passive_rx.cpp:87-158`: one high-priority core0 CAN owner receives both widths, 500k, accept-all, TX queue zero. Boot and nominal 100ms checks read all 49 physical GPIO output selectors; TXD route/inversion/output-enable selection, output enable/latch, sampled pin, IOMUX, input enable, push-pull, sleep/RTC mux; RX route/inversion and controller LOM/self-test/reset/state. More than 200ms between successful checks latches failure. A 5ms bounded RX wait and USB/UI on the other task keep reception from blocking the check. USB writes have a 10ms timeout.

On mismatch: detach all TX routes, reassert TXD HIGH, `twai_stop` + `twai_driver_uninstall`, latch CAN OFF with no reinstall/recovery, publish FAULT and teardown return codes. UI shows `PASSIVE FAULT`, USB logs `#PASSIVE_FAULT`. A stale check cannot keep a fresh VERIFIED UI status. `PASSIVE (TX ISOLATED)` requires a current successful check. The detector is sampled: it cannot prevent an arbitrary misrouting transient between checks, and total CPU/power failure prevents UI/log delivery. Static exclusion plus disconnected TX is the erratum defense; the periodic check is additional detection.

`src/passive_rx.cpp:165-262`: USB STATS every second/on demand: received frame/s and cumulative 11/29 counts, driver bus-error/arbitration-lost/drop counters, REC/TEC/state, self-check count/age and teardown results. No frames, IDs, VIN, location, BLE address or identity. Ring and active five-PID acquisition are deliberately unavailable. RX counters are successfully delivered frames, not proof of zero physical transmission or full wire utilization.

## Why B is not used

A generic ISO11898 error-passive controller can reduce REC after good reception, so a one-time REC=128 write is not a general invariant. However IDF4.4.7 [twai_hal.c:62-82](https://github.com/espressif/esp-idf/blob/v4.4.7/components/hal/twai_hal.c#L62) explicitly states that TEC/REC freeze in this hardware's Listen-Only mode and therefore considers REC=128 persistent **while LOM is maintained**. It would be inaccurate to claim that the generic decrement rule alone disproves that IDF workaround. A verified rebuild and continuous LOM/REC checks could support B; merely defining the Kconfig macro in an app does not rebuild Arduino's precompiled HAL. Current SDK has that fix unset and starts REC at zero. A is stronger: neither the counter's freezing/decrement behavior nor error-active internal dominant generation can reach TXD. No assumption of REC>=128 appears in this image's safety policy.

## Verification boundary

Separate negative compilation and ELF checks prevent future TX reintroduction. CI builds this env and runs these tests, plus the existing complete suites. Stubs verify implementation logic, not electrical behavior. UI fit, real reset-time bias, real routing-register values and ambient real CAN RX remain owner/PM acceptance. **No vehicle GO is inferred from a successful host test or build.**

See [short Japanese runbook](m5dial-passive-runbook.md). The former external-analyzer gate still applies to active/legacy environments. For this dedicated image only, owner-requested acceptance uses the routing proof, exact ELF/CI/hash and verified real-board startup instead; this does not claim an independent physical no-TX measurement.


## 2026-10-30 USB-only early FAULT incident (app-only hash verified; hardware diagnosis pending)

Owner/PM observed approximately 75 s of `#STATS` with `checks=0`, `self_check=FAULT`, `state=0`, `stop=0` and `uninstall=0`, following an app-only flash and reset. The monitor attached about 12 s after reset, so absence of the one-shot `#PASSIVE,git` line is **not** evidence that the line was never emitted. The legacy firmware was restored, and the full 8 MiB readback hash matched the backup. U179 power/attachment was not confirmed. The failure stage and actual input levels were **not recorded**; no specific electrical/driver cause is established.

Static code inspection contradicts a proposed ordering hypothesis: `holdTxdHigh()` is already the first statement in `setup()`, before `display.init()` and the `before` snapshot. Its latch-HIGH-before-output-enable sequence remains unchanged. The before-install software policy only substitutes RX routing, controller listen-only and running as *not yet applicable*; all TXD pin/RTC/IOMUX and TX-route conditions remain required. ESP-IDF v4.4.7 documents `gpio_config` (GPIO mode), `rtc_gpio_deinit` (RTC-to-digital mux) and `gpio_sleep_sel_dis` separately; do **not** assume `gpio_config` clears an arbitrarily retained sleep setting. Neither the actual GPIO13 reset pad level nor `RTC_IO_TOUCH_PAD13_MUX_SEL` state, `SLP_SEL`, or the result of `display.init()` can be deduced from a 12-s-late serial log. GPIO13 is PORT.A TXD and is *not* an LCD SPI pin (LCD GPIO4–9; official M5Dial pin map). With U179 unverified, `txd_pad_high` is plausible but unconfirmed. The fake SDK's previous default-high pad and reset registers were insufficient to distinguish these early failures.

The revised firmware records **the first failure only**, then detaches every TWAI_TX GPIO route, reasserts TXD HIGH, stops/uninstalls the driver if installed, and publishes the evidence. The initial USB line and a 1 Hz replay have the form:

```
#PASSIVE_FAULT,stage=<stage>,field=<first rejected condition>,code=<driver result>,no_tx_routes=<0/1>,txd_gpio=<0/1>,txd_enabled=<0/1>,txd_latch_high=<0/1>,txd_pad_high=<0/1>,txd_mux_gpio=<0/1>,txd_input_enabled=<0/1>,txd_push_pull=<0/1>,txd_awake=<0/1>,rx_route=<0/1>,controller_listen_only=<0/1>,running=<0/1>,iomux_sleep_sel=<0/1>,rtc_touch13_mux_sel=<0/1>
```

Stages: `display_init` (LCD init returned false), `before_snapshot` (after TXD HIGH, before install), `driver_install`, `stopped_snapshot` (post-install, TX detached), `driver_start`, `initial_check` (first started controller check), `task_create`; runtime stages `periodic_check` and `receive`. The first policy-failing field or failing API is provided separately; `code` is the API return value for driver calls. Snapshot booleans preserve **raw observation**, rather than the not-yet-applicable substitutions used to check pre-start invariants. In a pre-install snapshot `rx_route=0`, `controller_listen_only=0`, and `running=0` do not by themselves indicate a TX safety failure. `txd_awake=0` covers the IO_MUX sleep-select **or** RTC TOUCH13 MUX_SEL condition. Diagnostic-only `iomux_sleep_sel` and `rtc_touch13_mux_sel` independently report which bit was set; `passive::safe` still requires `txd_awake` as before. GPIO13/HOLD and LCD failures must remain fail-closed.

No safety predicate was removed, no CAN output capability was added, no prior early-fault state is considered acceptable. The additional LCD draw guard prevents calls to an uninitialized display after `display.init()` returns false, keeping serial diagnosis available. Host tests now model pre-boot GPIO13 pad LOW, RTC mux retained, IOMUX/sleep/input anomalies, post-install RX route mismatch, first-check mode/status failure and late serial attachment. These are model-level injection tests, not proof of the physical GPIO electrical state.

**Approval remains NO-GO** until the PM/owner performs the existing USB-only bench runbook on an exact verified image, archives the new startup fault/stats output, confirms the actual U179 wiring/power, and obtains a 60 s clean self-check with no vehicle connection. No active/vehicle firmware permit follows from this patch.


## 2026-10-30 cb60f10 bench evidence: GPIO13 route/output-enable lost before installation

The PM observed this **on USB only, no CAN or vehicle** (U179 presence/power unverified):
`stage=before_snapshot,field=txd_gpio,code=0,no_tx_routes=1,txd_gpio=0,txd_enabled=0,txd_latch_high=1,txd_pad_high=0,txd_mux_gpio=1,txd_input_enabled=1,txd_push_pull=1,txd_awake=1,rx_route=0,controller_listen_only=0,running=0,iomux_sleep_sel=0,rtc_touch13_mux_sel=0`. All ARM/lease commands were rejected. The old application was restored with the full 8 MiB readback hash verified.

**Established**: GPIO13 output route/OE had been lost by the pre-install inspection, although its data latch was HIGH and IOMUX/input remained valid. This occurred after the first `holdTxdHigh()` but before install. The only intervening application calls are HOLD GPIO46, LCD `display.init()/setBrightness`, and USB serial init. A peripheral init/deinit interaction is plausible; the log does **not** prove whether the first `holdTxdHigh` actually succeeded or specifically which call cleared the route/OE. No RTC MUX or sleep selection mismatch was observed. The new `#PASSIVE_BOOT` log records first-hold and post-display snapshots to distinguish these hypotheses on the next USB-only bench. `gpio_config` and `gpio_set_level` are specified by ESP-IDF to set mode and output latch respectively, while `gpio_get_level` reads 0 if pad input is disabled; GPIO13 input was enabled in this incident.

**Containment correction**: retain the first `holdTxdHigh` as the first application action, and require a full GPIO13/route safety snapshot immediately after it, before display initialization. After LCD initialization, take a separate snapshot. If **all** existing safety fields remain true, continue without additional writes. If and only if the output gate is disabled (`txd_enabled=0`) while the data latch is HIGH, no TWAI output route exists, and mux/input/push-pull/awake are correct, reapply HIGH-latch-first GPIO configuration once, then demand **all original safety fields including `txd_pad_high=1`** again before installing TWAI. Any enabled misrouted output, LOW latch, RTC/IOMUX fault, readback failure, LCD failure or post-reassert mismatch latches FAULT. This is not a general self-healing path; there is no retry after TWAI install, and no downgrade of the original `passive::safe` predicate.

**Electrical limitation**: from snapshots only at the boundaries, it is impossible to prove that GPIO13 never became LOW **during** `display.init()`, nor to establish whether it was weakly pulled versus driven during that interval. In the observed final state `GPIO.enable[13]=0`, there was no digital output enabled at the sampled instant, and the program kept the HIGH latch; this rules out a GPIO data-latch LOW drive *at that instant*, not a brief transient. A correctly powered TJA1051T/3 has an internal TXD pull-up to VIO to hold recessive when the MCU is high impedance. Without a connected and powered U179, **do not assume the external TXD pull-up exists**. Nevertheless, once GPIO13 is correctly configured as MCU push-pull HIGH and sampled as input, a disconnected U179 should not by itself make the MCU pad LOW; continued `txd_pad_high=0` requires investigation of the MCU/connection, and remains FAULT. An external LOW contention may keep the sampled pad LOW, which must never be ignored.

**Approval**: host-model successes and a green ELF/CI alone do not prove uninterrupted recessive TXD on the physical pin. Because the observed pad was LOW when output was disabled, *vehicle/CAN connection remains NO-GO* until U179 presence/power and the new desk boot logs are confirmed, with optional GPIO13 electrical observation if proof of no transition is required. No app-only flashing or vehicle manipulation is performed by the implementation agent.
